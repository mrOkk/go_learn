# Task

Сервис процессинга платежей.

Система получает поток транзакций из Kafka, проверяет статус мерчанта в базе данных PostgreSQL и сохраняет финальный статус транзакции. Для снижения нагрузки на PostgreSQL необходимо использовать LRU-кэш для хранения данных о мерчантах.

## Технологический стек

- **Язык**: Go (чистый код, стандартная библиотека + драйверы)
- **Брокер**: Apache Kafka
- **СУБД**: PostgreSQL
- **Паттерны**: LRU Cache, Worker Pool

## Архитектурные требования

### 1. Стриминг и партиционирование (Kafka)

- Использовать Kafka-топик `transactions`.
- Топик должен иметь не менее 3 партиций (шардов).
- Ключом партиционирования должен быть `merchant_id`. Это гарантирует, что транзакции одного и того же мерчанта всегда попадают в одну и ту же партицию и обрабатываются строго последовательно.
- Реализовать чтение через Consumer Group.

### 2. База данных (PostgreSQL)

- Таблица `merchants` (`id`, `name`, `is_active`, `balance`).
- Таблица `transactions` (`id`, `merchant_id`, `amount`, `status`, `timestamp`).

### 3. Сервис на Go (Consumer + Processor)

- Приложение запускает Worker Pool, где количество воркеров равно количеству партиций Kafka.
- Каждый воркер читает свой шард (партицию) Kafka.
- **LRU кэш**:
  - Реализовать собственный LRU-кэш фиксированного размера (например, на 1000 элементов) для хранения структуры `Merchant`.
  - Кэш должен быть потокобезопасным (`sync.RWMutex`), так как к нему будут обращаться разные воркеры.
- **Логика обработки сообщения**:
  - Приходит транзакция.
  - Проверяем мерчанта в LRU-кэше.
  - Если в кэше нет (Cache Miss) — идем в Postgres, сохраняем в кэш.
  - Если мерчант заблокирован (`is_active = false`), транзакция отклоняется (`status = rejected`).
  - Если активен — обновляем баланс мерчанта и сохраняем транзакцию со статусом `approved`.

### 4. Надежность и отказоустойчивость

- **Graceful Shutdown**: Приложение должно корректно завершать работу по сигналу `SIGINT/SIGTERM` (дочитать текущие сообщения, закрыть соединения с БД и Kafka).
- **At-Least-Once**: Смещение (offset) в Kafka должно фиксироваться (commit) только после того, как транзакция успешно записана в PostgreSQL.
