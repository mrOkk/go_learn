## Обновление 2 (повторная проверка `internal/registry/registry.go` после очередных правок)

Файл снова изменился между ревью. Проверены все три ранее найденные критические находки:

- **Бывший пункт 1 (`Snapshot()` возвращает пустой слайс) — устранён.** Теперь
  `backends := make([]*Backend, len(r.backends)); copy(backends, r.backends)` — корректно, подтверждено
  тестом (`len(Snapshot()) == 3` после трёх регистраций).
- **Бывший пункт 2 (`NewRegistry` создаёт слайс с 4 nil-элементами) — устранён.** Теперь
  `make([]*Backend, 0, 4)` — нулевая длина, только запас ёмкости.
- **Бывший пункт 3 (индексы в `backendsMap` не пересчитываются после `Deregister`) — устранён.**
  `Deregister` теперь перестраивает `backendsMap` для всех сдвинутых элементов (цикл
  `for i := bIndex; i < len(r.backends); i++`). Подтверждено тестом: регистрация 3 бэкендов →
  `Deregister` первого → `Heartbeat` на оставшиеся двух проходит без ошибок и без паники.

Однако при проверке `sweep()` (аналогичная логика удаления, но не пофикшенная так же, как `Deregister`)
найден **новый критический баг**, который заменяет прежний пункт 3.

## 🔴 Критично

### 1. `sweep()` мутирует слайс во время итерации `range` — паника процесса
Файл: `internal/registry/registry.go:89-105`

```go
func (r *Registry) sweep(now time.Time) {
	r.mu.Lock()
	defer r.mu.Unlock()
	anyDeleted := false
	for i, b := range r.backends {
		if now.Sub(b.LastSeen) > r.ttl {
			r.backends = slices.Delete(r.backends, i, i+1)
			delete(r.backendsMap, b.Id)
			anyDeleted = true
		}
	}
	...
```

`range r.backends` вычисляет и фиксирует заголовок слайса (указатель на массив + длину) один раз при
входе в цикл. Внутри цикла `slices.Delete(r.backends, i, i+1)` физически сдвигает элементы влево
**в том же массиве** и, что важно, **зануляет освободившийся хвостовой слот** (внутренняя реализация
`slices.Delete` очищает "хвост", чтобы не удерживать указатели от сборщика мусора). Захваченный `range`
заголовок слайса продолжает итерацию по исходной длине и исходному указателю на массив — следующие
итерации читают из позиций, которые уже были обнулены/сдвинуты `slices.Delete`, и получают `b == nil`,
после чего `b.LastSeen` (следующая итерация цикла) — `nil pointer dereference`.

Баг воспроизведён тремя разными способами:

1. Прямой вызов `sweep()` при одном протухшем бэкенде среди трёх (протухает первый по порядку,
   переживают второй и третий, живших дольше):
   ```
   panic: runtime error: invalid memory address or nil pointer dereference
       registry.go:94 (Registry.sweep)
   ```
2. То же с двумя протухшими из четырёх (не смежными по индексу) — паникует так же.
3. **Через публичный API и реальный жизненный цикл**: фоновая горутина `SweepJob` (именно так она
   запускается в `cmd/main.go: go reg.SweepJob(ctx, cfg.GRPC.Timeout/3)`), при протухании одного из
   двух бэкендов, паникует внутри горутины:
   ```
   panic: runtime error: invalid memory address or nil pointer dereference
   goroutine 8 [running]:
   LoadBalancer/internal/registry.(*Registry).sweep(...)
       registry.go:94
   LoadBalancer/internal/registry.(*Registry).SweepJob(...)
       registry.go:84
   ```
   Паника в горутине без `recover` **завершает весь процесс** — это не изолированная ошибка одного
   запроса, а полный отказ сервиса. Причём это штатный, ожидаемый сценарий работы (TTL-протухание
   неактивного бэкенда), а не редкий edge case — он будет срабатывать в любой инсталляции, где хотя бы
   один бэкенд перестаёт слать heartbeat, а другие продолжают.

**Рекомендация:** не мутировать слайс во время `range` по нему. Варианты:
- Собрать список идентификаторов/индексов на удаление в отдельный слайс во время прохода, затем
  выполнить все `slices.Delete` после цикла (в порядке убывания индексов, чтобы не сбить более ранние).
- Либо построить новый слайс "выживших" через `slices.DeleteFunc(r.backends, func(b *Backend) bool {...})`
  и один раз пересчитать `backendsMap` (как уже сделано в `Deregister`).
- Обязательно покрыть тестом с ≥2 протухшими бэкендами среди ≥3 живых, чтобы поймать регресс на этом месте
  повторно — эта функция уже дважды переписывалась между итерациями ревью и оба раза оставалась битой.

Confidence: 10/10

### 4. Утечка gRPC-соединений в пуле бэкендов
Файл: `internal/adapters/grpcclient/pool.go:16-32`

`Pool.get` кэширует `*grpc.ClientConn` по адресу навсегда; метод `Close(address)` существует, но нигде не
вызывается — ни при `Deregister`, ни при sweep-удалении протухшего бэкенда. При смене адресов бэкендов
(рестарты, динамическое окружение) пул бесконечно копит «мёртвые» соединения без возможности их закрыть.

**Рекомендация:** вызывать `pool.Close(address)` при дерегистрации/протухании бэкенда (например, через
callback/канал из `Registry`).

Confidence: 8/10
